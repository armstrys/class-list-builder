# Security Audit — v3.3.1

**Nature of this release:** two correctness fixes for features shipped

### The defect

`loadCriteriaFromStorage` in `src/contexts/index.js` gained a
`category` key in its `catch` (fallback) return path but **not** in its
`try` (normal) path. On the normal path `criteria.category` was
therefore `undefined`, and `SettingsModal` calls
`categoryCriteria.some(...)` during render. Opening Settings threw
`Cannot read properties of undefined (reading 'some')`, which unmounted
the tree and produced a blank page.

A second defect surfaced in the same area: v3.3.0 never surfaced the
category value in the roster table, and sample data generation never
populated it, so the field appeared to do nothing even once Settings
worked. Both were fixed here — the table now renders a column per
category criterion, and `generateSampleStudents` assigns each student a
prior room so the demo exercises the feature.

A third defect followed immediately: the new roster column was inserted
in the body **before** the flag cells while the header listed it
**after** them, so the "Current Class" header sat above the flag check
marks and every value to its right was mislabelled. Both now emit
`numeric → flag → category` in the same order, and a test asserts the
header and body sequences are identical.

That also exposed a presentation problem: a category cell is free text,
not a yes/no, and must not read like a flag check mark. Category cells
now render the value as a dashed chip (`.cat-chip`), visually distinct
from the solid colour badges used for flags.

Finally, the value was missing from every summary surface. It now
appears per class on the Optimize board, in the printed report's
per-class badges, and — for the mis-spelling case — as a list of the
distinct values actually observed in the roster, in Settings under
Category Fields. That last one matters because values are stored
verbatim: `Ms. Rivera` and `Ms Rivera` become two categories and quietly
halve the spread. The counting lives in one shared helper
(`countCategoryValues`) rather than three copies, and trims values
before bucketing so a trailing space is not a phantom category.

Neither defect was cache-dependent: it reproduced on a fresh install, a stale
v3.2.0 cache, a cache containing the category key, and a corrupt cache.
It only appeared to be a cache problem because the feature looked absent
as well (the new default never loaded, for the same reason).

Found by rendering the real component tree in Node against the real
React 18 runtime with the sources concatenated exactly as
`build-standalone.js` concatenates them, rather than by inspection.
Verified fixed in all four cache states.

Impact is availability only: no data was exposed or corrupted. A user
who hit it lost the Settings surface, and since "Clear Cache" lives
inside Settings, the documented workaround was unreachable.

## Methodology

- The crash was reproduced by concatenating all `src/**` into one script
  (the shipped bundle's structure), transforming with the same Babel
  standalone the app uses, and rendering `SettingsModal`, `SetupPage`,
  `OptimizePage`, `StudentFormModal`, `PrintReportView` and `HelpModal`
  inside their real context providers.
- Ran against four seeded `localStorage` states: empty, stale v3.2.0
  (no category key), current, and corrupt (non-array JSON). All seven
  components render in all four states after the fix.
- Added 24 regression tests: 6 covering the loader's return shape on
  every path (including that the exact `categoryCriteria.some(...)` call
  the modal makes cannot throw), and 4 covering sample-data population,
  the absence of the key when no criteria exist, the roster table
  rendering both a header and a cell per criterion, and the sample
  generator being wired to the category criteria in both call sites;
  and 14 covering `countCategoryValues` (trimming, misspelling visibility,
  blanks/nulls/missing lists) plus header/body column-order equality, the
  category cell rendering text rather than a check mark, and each of the
  three summary surfaces referencing category data.
- Hardened `SettingsModal` to default the array to `[]`, so a future
  loader regression degrades to "no category fields" rather than a blank
  page.
- All four surfaces were verified by rendering them with seeded
  students containing a deliberate typo: the roster shows the
  "Current Class" header with text values (2 check marks, matching the
  2 real flags); the Optimize footer and the print report both show
  `Current Class: Ms. Rivera 2 · Mr. Okafor 1`; and Settings reports
  "3 distinct values" listing `Ms. Rivera`, `Mr. Okafor` and the
  misspelled `Ms Rivera` together with the near-duplicate warning.
- The roster table was verified by rendering `SetupPage` with the
  seeded sample students inside stubbed context providers: the
  "Current Class" header and "Room A/B/C" cells all appear
  (10461 chars rendered, versus 2257 for the empty table).
- Full suite (302 tests), lint, standalone build and
  `scripts/validate-build.js` run against the final tree.
- `node .security/scripts/audit-hash.js`, then
  `node .security/scripts/verify-audit.js` to confirm.

## Vulnerability Findings

No security findings. One availability defect (described above) was
found and fixed; it carried no confidentiality or integrity impact.

For completeness, the two informational findings from v3.3.0 remain
accurate and were re-confirmed against the current tree: category values
are free text rendered only through React text interpolation (no
`dangerouslySetInnerHTML` / `innerHTML` / `eval` / `new Function`
anywhere in `src/`), and category *values* are never written to
localStorage.
