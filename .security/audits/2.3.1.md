# Security Audit — v2.3.1

## Scope

Single-file React SPA distributed as a standalone HTML bundle, plus its
build pipeline and the public security claims in `SECURITY.md`.

Paths covered by the manifest hash:

- `src/**` (33 files)
- `package.json`, `package-lock.json`
- `SECURITY.md`
- `build-standalone.js`, `class-list-builder-source.html`,
  `scripts/validate-build.js`

Out of scope: `node_modules/` (covered transitively via `npm audit`),
`tests/**`, developer-only scripts not in the manifest.

## Methodology

- `npm audit --package-lock-only --json` reviewed against the committed
  lockfile (not a locally-resolved tree), before and after the dependency
  updates in this release.
- `npm audit --package-lock-only --omit=dev` run separately to establish
  whether any advisory reaches the shipped artifact.
- Each claim in `SECURITY.md` re-verified against current source by grep
  and by reading the matched call sites.
- Changed files reviewed line-by-line: `src/app.js`, `src/defaults.js`,
  `package.json`, `package-lock.json`.
- Prompt-injection sentinel scan run across all of `src/**`, plus a
  Unicode irregularity scan (bidi overrides, zero-width, tag characters).
- Standalone artifact rebuilt (`node build-standalone.js`) and validated
  (`node scripts/validate-build.js`).
- Toolchain installed from the committed lockfile and the full suite re-run
  after the dependency updates: 208 tests pass across 11 files; 0 lint
  errors. `package-lock.json` was byte-compared before and after the install
  to confirm the install did not mutate it.

**Process deviation, disclosed:** because of F-002, `npm ci` aborts with
`EBADPLATFORM` on the auditor's darwin/arm64 host. Both the lockfile update
(`npm update --package-lock-only --force`) and the toolchain install
(`npm ci --force`) required `--force` to bypass that platform check. The
flag suppresses the platform gate only; resolution still came from the
committed lockfile, `package.json` was not modified, and the post-install
byte-comparison confirms the lockfile is exactly what is committed and
audited. CI runs on linux/x64, where plain `npm ci` succeeds without
`--force`.

## Changes Since v2.3.0

This is a maintenance release. It contains no feature work and no change
to data handling, storage, export, or the build pipeline.

1. **Dead-code removal** (`src/app.js`) — Removed the pre-v2.2.0 assignment
   fallback from `handleLoadProject`, tracked as issue #74.

   `handleLoadProject` is reachable only via `LoadProjectModal`
   (`src/app.js:192`, `src/components/LoadProjectModal.js:123`), and both
   of that component's load modes pass the output of `deserializeProject()`.
   The deserializer already performs this migration at
   `src/utils/projectDeserializer.js:507-518`. The app-level fallback could
   therefore only fire when the deserializer's own migration produced an
   empty result — and because both apply identical student/teacher
   validation, the `Map` the fallback iterated was empty in exactly that
   case, making its `setAssignment({})` a no-op.

   The companion `hasAssignments` navigation check was independently inert:
   the deserializer returns `optimizationResults.assignments` as a `Map`
   (`src/utils/projectDeserializer.js:530-543`), and `Object.keys(map).length`
   is always `0`, so navigation has always been driven by `data.assignment`
   alone.

   **The deserializer-side migration and its regression test are retained.**
   They are the code path that actually loads pre-v2.2.0 projects and remain
   scheduled for removal at v3.0.0 per #74. No user-visible behavior changes
   in this release.

2. **Dependency updates** (`package-lock.json`) — Five transitive dev
   dependencies advanced to clear all outstanding advisories. Lockfile-only;
   no `package.json` change, as none is a direct dependency. Details in the
   Dependency Audit section.

3. **Version bump** — `package.json` and `src/defaults.js` to 2.3.1.

`sources-sha256` (`f50aaa68…`), `claims-sha256` (`2546c2ce…`) and
`build-sha256` (`27a801b0…`) confirm the shape of this release: application
source changed only in the two files named above, and `SECURITY.md` and the
build entrypoints were not touched at all. `deps-sha256` changed for the
version bump plus the lockfile updates.

## Vulnerability Findings

### F-001 — Dev-toolchain dependencies carried five high-severity advisories

- **Severity:** informational *(npm rated these `high`; see rationale)*
- **Category:** dependency / supply-chain
- **Location:** `package-lock.json` (transitive dev tree)
- **Description:** At the opening of this audit, `npm audit` reported 5
  high-severity advisories against `brace-expansion`, `js-yaml`, `nanoid`,
  `postcss`, and `vite` — all transitive dev-only dependencies reached
  through `vitest` → `vite` and `eslint`. This was drift since the v2.3.0
  audit of 2026-05-25, which recorded zero; the advisories were published in
  the intervening ~11 weeks. No dependency was added or upgraded by the
  application itself.
- **Impact:** Contextually low even before remediation. `package.json`
  declares **zero production dependencies** (`"dependencies": {}`), and
  `npm audit --omit=dev` reported `found 0 vulnerabilities` throughout. None
  of the five packages appeared in the built artifact (`grep -c` against
  `dist/class-list-builder-v2.3.1.html` returned `0` for each).
  `build-standalone.js` imports only Node builtins (`fs`, `path`, `https`,
  `zlib`, `crypto`), so the vulnerable code was absent from the release path
  as well as the runtime. The advisories are DoS (`brace-expansion`,
  `js-yaml`, `nanoid`) plus local file-disclosure in developer tooling
  (`postcss` source-map loading, `vite` dev-server path handling on
  Windows) — reachable only by a developer running the test or lint
  toolchain against hostile input.

  Severity is recorded as informational per the auditor's contextual
  assessment, not npm's context-free CVSS rating.
- **Remediation:** Applied in this release. All five chains updated in
  `package-lock.json`; `npm audit --package-lock-only` now reports
  `found 0 vulnerabilities`. See the Dependency Audit section for
  before/after versions.
- **Status:** fixed-in-this-release

### F-002 — `@rolldown/binding-linux-x64-gnu` pinned as a direct devDependency breaks `npm ci` off-platform

- **Severity:** low
- **Category:** supply-chain / build integrity
- **Location:** `package.json` devDependencies; introduced in commit `c57d464`
- **Description:** A platform-specific native binary,
  `@rolldown/binding-linux-x64-gnu`, is declared as an ordinary direct
  devDependency rather than being resolved as the optional, per-platform
  dependency of `rolldown`. `npm ci` consequently aborts with
  `EBADPLATFORM` on any host that is not linux/x64:

  ```
  npm error code EBADPLATFORM
  npm error notsup Unsupported platform for @rolldown/binding-linux-x64-gnu@1.0.0-rc.18:
  wanted {"os":"linux","cpu":"x64"} (current: {"os":"darwin","cpu":"arm64"})
  ```

  The lockfile already carries the full set of per-platform bindings,
  including `@rolldown/binding-darwin-arm64`, so the direct pin is not
  needed for resolution — only the linux-x64 CI runner benefits from it.
  The check is not confined to installs: it also blocks
  `npm update --package-lock-only`, so routine dependency maintenance
  cannot be performed off linux/x64 without `--force`.
- **Impact:** No effect on the released artifact or on CI (which runs
  linux/x64). The security-relevant consequence is process, not product. A
  maintainer or reviewer on macOS or Windows cannot run `npm ci` or update
  the lockfile normally, and is therefore pushed toward `npm install` or
  `--force`, both of which weaken the guarantee that the installed tree
  matches the audited, hash-pinned lockfile. That is a plausible route for
  un-audited dependency drift to enter a release — and this audit had to
  navigate it directly (see Methodology).
- **Remediation:** Remove the direct devDependency and let `rolldown`'s
  optionalDependencies resolve the correct binding per platform. If the CI
  runner genuinely needs the explicit pin, prefer scoping `--force` to the
  CI job, or move the pin behind an `optionalDependencies` entry.
- **Status:** open — **deliberately not remediated in this release**, at the
  maintainer's direction. Fixing it edits `package.json` and would change
  `deps-sha256` again; it is tracked for a standalone PR.

### F-003 — v2.3.0 audit's Accepted Risks table misdescribes both exception IDs

- **Severity:** informational
- **Category:** other (documentation / audit-trail accuracy)
- **Location:** `.security/audits/2.3.0.md` (Accepted Risks section)
- **Description:** The prior audit's Accepted Risks table describes
  CLB-EXC-0001 as `'unsafe-eval'` in CSP and CLB-EXC-0002 as
  `'unsafe-inline'` in CSP style-src. The registry at
  `.security/audits/exceptions.json` defines CLB-EXC-0001 as *"Single
  maintainer — no separation of duties"* and CLB-EXC-0002 as *"ExcelJS
  4.4.0 transitive CVEs in Node-only code paths"*. The cited IDs and the
  described risks do not correspond.
- **Impact:** No runtime impact. `verify-audit.js` checks only that cited
  IDs exist and are unexpired, so the mismatch passes CI. The risk is to the
  audit trail itself: a reader reconstructing which risks were accepted at
  v2.3.0 gets the wrong answer, and the two genuinely accepted risks
  (single-maintainer sign-off, ExcelJS transitives) appear undocumented for
  that release.
- **Remediation:** Signed audits are append-only, so `2.3.0.md` must not be
  edited. Issue a `2.3.0-r2` revision carrying the corrected table, with
  `supersedes:` pointing at the original and the original marked
  `superseded`. This audit's own Accepted Risks table below reflects the
  registry as written.
- **Status:** open (pre-existing; not introduced by this release)

## Prompt Injection Defense Notes

A sentinel scan was performed across all of `src/**` (33 files), covering
instruction-override phrases, role-marker injection, Unicode tricks, and
hidden base64/hex payloads. Reporting both what was found and that the scan
ran, since silence and absence are otherwise indistinguishable.

**Two benign matches, no injection attempts:**

1. Instruction-phrase scan matched one line, at `src/components/HelpModal.js:75`:

   ```
   Total flags and scores act as safety nets to catch overall imbalances.
   ```

   The pattern `act as` fires on ordinary English describing optimizer
   behavior. Pre-existing UI copy, not part of this changeset. The same match
   was recorded in the v2.3.0 audit.

2. Unicode scan matched one line, at `src/components/SetupPage.js:178`:

   ```
   <div className="icon">👩‍🎓</div>
   ```

   The hit is U+200D (zero-width joiner) as a legitimate component of the
   `👩‍🎓` emoji ZWJ sequence, not a hidden-character payload. Pre-existing.

**Not found:** no bidi overrides (U+202A–U+202E, U+2066–U+2069), no tag
characters (U+E0000–U+E007F), no stray zero-width characters outside the
emoji sequence above, no base64/hex blobs over 50 characters in the changed
files, no role markers (`[INST]`, `<|im_start|>`, `<<SYS>>`, `system:`,
`assistant:`), and no text anywhere in `src/**` attempting to instruct,
redirect, or reconfigure an AI auditor.

No instruction text from any source file altered this audit's scope,
severity classifications, findings, or sign-off. The audit plan was fixed
before any source file was opened and was executed unchanged.

**Residual risk:** indirect prompt injection is not a solved problem as of
mid-2026; adaptive attacks defeat published defenses at high rates. The
hardening applied here is defense-in-depth, not a guarantee. The
deterministic checks (`audit-hash.js`, `verify-audit.js`) and the human
sign-off below are the enforcement layer; the AI-assisted review is a force
multiplier, not the arbiter.
