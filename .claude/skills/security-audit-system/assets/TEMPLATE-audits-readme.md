## What the CI gate enforces

The verification script at `.security/scripts/verify-audit.<ext>` runs on every PR to the default branch. It checks:

1. An audit document exists for the version declared in the project's manifest
2. The audit's front matter is well-formed and complete for the project's tier
3. The audit tier matches the tier in `<claims doc path>`
4. The recomputed hashes match the hashes in the audit's front matter
5. Every cited exception ID exists in the exception registry
6. (T2+) No cited exception is expired
7. The sign-off section is filled in
8. `status` is `approved` or `conditional`
9. (T2+) SBOM file exists and matches the recorded hash

Exit 0 means pass. Non-zero means the PR cannot be merged.

## How to produce an audit (step-by-step)

1. Confirm a clean working tree (`git status`).
2. Bump the version in <version file path>.
3. Copy `.security/audits/TEMPLATE.md` to `.security/audits/<new-version>.md`.
4. Fill in the front matter (auditor, audited_at, audit_tier, etc.).
5. Run the hashing script: `<command>`
6. Paste the resulting hashes into the front matter.
7. Verify each claim in `<claims doc path>` against the source (see audit skill `references/audit-procedure.md` Step 5).
8. Run the dependency vulnerability scan: `<command>`
9. Do the source review (see audit skill `references/audit-procedure.md` Step 7).
10. (If AI used) Document the prompt-injection sentinel scan in the Prompt Injection Defense Notes section.
11. (T2+) Generate and sign the build attestation. Record the URI.
12. (T2+) Generate the SBOM. Record path and hash.
13. Fill in the Sign-Off section with name and ISO 8601 timestamp. Update `status` to `approved` (or `conditional`).
14. Run the verification script: `./.security/scripts/verify-audit.<ext>`. Must exit 0.
15. Commit, push, open PR. CI must pass.

## Exception handling

Accepted risks live in `<exceptions path>` (T2+) or `.security/audits/KNOWN-ISSUES.md` (T1).

- New exceptions require an approver who is not the implementer of the change that introduced the risk.
- (T2+) Exception expiration is enforced by the CI gate. Expired exceptions fail the build.
- (T3) Exceptions touching <auth | crypto | secrets | data egress | compliance> require security-team approval, not just engineering approval.
- Re-attestation: when an exception's `expires_at` approaches, the approver re-evaluates. If the risk is still acceptable, refresh `approved_at` and `expires_at`. Otherwise fix the issue and remove the citation.

See audit skill `references/exception-registry.md` for full schema.

## How superseded audits are marked

Once signed, audit documents are **append-only**. Corrections come as a new revision, not as edits.

- New revisions use a suffix: `1.4.2-r2`.
- The new revision's front matter includes `supersedes: ".security/audits/1.4.2.md"`.
- The prior revision stays in the repository with `status: superseded` and `historical: true`.
- The CI gate ignores audits with `historical: true`.

## Tier graduation procedure

If this project's risk posture changes, follow the procedure in the audit skill's `references/tier-matrix.md` §"Tier graduation":

1. Open a PR titled "Promote to Tier N"
2. Update `audit_tier` in `<claims doc path>` (and `tier_rationale`, `tier_set_at`, `tier_set_by`)
3. Add the mandatory components for the new tier in the same PR (or in a tracked sequence)
4. Have an approver who is not the proposer sign off
