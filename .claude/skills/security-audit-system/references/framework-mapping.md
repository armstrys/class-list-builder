# Framework Alignment Reference

The audit system's outputs map to established frameworks. The mappings are informational at Tier 1, recommended at Tier 2, and **required (as an explicit table in the audit document) at Tier 3**.

This reference is consulted when a stakeholder asks: *"How does our audit system relate to SLSA / SSDF / Scorecard / SOC 2 / CIS?"* The answer is given as a table mapping each framework's requirements to system components.

---

## SLSA (Supply-chain Levels for Software Artifacts)

| SLSA Build Level | What this system produces |
|---|---|
| L0 | Tier 0 — none required |
| L1 | Tier 1 — machine-readable provenance via CI logs and audit document (if extended with provenance generation) |
| L2 | Tier 2 — signed in-toto Statement covering release artifacts, signed by the hosted build platform |
| L3 | Tier 3 — isolated builder with unforgeable provenance (builder-provided generator running in a separate trust boundary from user-defined build steps) |

### Common pitfalls

- **Provenance generated by the build script itself is forgeable.** To reach L3, the provenance generator must run in a builder isolated from user-controlled build steps. Builder-provided generators (platform-native attestation actions, Tekton Chains) are the typical path.
- **Self-hosted runners with reused VMs** can leak state between builds → fails L2 isolation requirement. Use ephemeral runners.
- **Secrets accessible to build steps** can be exfiltrated by malicious dependencies → fails L3. Use OIDC-issued short-lived credentials, never long-lived secrets in build env.

## NIST SSDF (SP 800-218)

| SSDF Practice | Audit-system element |
|---|---|
| PO.5 (toolchains) | Hashing and verification scripts; CI integration |
| PS.1 (protect from access) | Branch protection, required reviewers |
| PS.2 (provide integrity verification) | Signed attestations (T2+) |
| PS.3 (archive each release) | Audit document + SBOM + attestation per release |
| PW.2 (review design) | Threat model document (T3) |
| PW.4 (reuse secure components) | Dependency scan, SBOM, vetted-dependencies policy |
| PW.6 (review/test) | Per-release audit document; AI-assisted review |
| PW.7 (additional pre-release review) | Sign-off step; separation of duties (T2+) |
| PW.8 (secure build/deploy config) | Build attestation; reproducible builds (T3) |
| PW.9 (default secure config) | Claims verified by audit |
| RV.1 (vulnerability intake) | Claims document reporting channel + `security.txt` |
| RV.2 (prioritize/remediate) | Exception registry with severity-tiered expiration |
| RV.3 (root-cause analysis) | Findings with category and remediation guidance |

A T3 project includes this mapping in the audit document directly, with column 3 "Evidence" pointing to the specific artifact (e.g., `.security/audits/1.2.0.md §Sign-Off`).

## OpenSSF Scorecard

Scorecard scores OSS projects on 18+ heuristic checks. The audit system materially improves these:

| Scorecard Check | How this system helps |
|---|---|
| Binary-Artifacts | Audit's source-review step flags vendored binaries |
| Branch-Protection | Branch protection enforced at T1+ |
| CI-Tests | CI gate requires audit verification |
| Code-Review | Required PR review at T1+; separation of duties at T2+ |
| Contributors | (not directly addressed) |
| Dangerous-Workflow | Source review covers CI configs at T2+ |
| Dependency-Update-Tool | Recommended in `.security/audits/README.md` |
| Fuzzing | (not directly addressed) |
| License | LICENSE checked via `file_exists` or `file_hash_matches` claim |
| Maintained | Audit cadence demonstrates activity |
| Packaging | Build attestation at T2+ |
| Pinned-Dependencies | `dependency_pinned` claims verify this |
| SAST | Recommended at T2+; results referenced in audit |
| Security-Policy | Claims document at T1+ |
| Signed-Releases | Build attestation at T2+ |
| Token-Permissions | Source review at T2+ |
| Vulnerabilities | Dependency vulnerability scan at T1+ |
| Webhooks | (not directly addressed) |

Running OpenSSF Scorecard alongside the audit system gives both a third-party score and a per-release human-signed audit. They complement each other; neither replaces the other.

## SOC 2 CC8.1 (Change Management)

SOC 2 Common Criteria 8.1 requires that the organization "authorizes, designs, develops or acquires, configures, documents, tests, approves, and implements changes to infrastructure, data, software, and procedures to meet its objectives."

How this system addresses each verb:

| CC8.1 element | System element |
|---|---|
| Authorizes | PR-based change with required reviewer; T3 requires two strongly-authenticated reviewers |
| Designs | Threat model document (T3); architectural decisions captured in PRs |
| Documents | Audit document per release; claims document; exception registry |
| Tests | Audit verification script; CI gate; dependency scan |
| Approves | Sign-off step with separation of duties (T2+) |
| Implements | Release pipeline contract with signed attestation (T2+) |

SOC 2 auditors typically want evidence of *each* element for *each* change. The audit document + git history + CI logs provide this evidence.

## CIS Software Supply Chain Security Guide

CIS publishes a software supply chain benchmark. Selected mappings:

| CIS Recommendation | System element |
|---|---|
| 1.1.1 — Restrict access to source code repositories | Branch protection (T1+) |
| 1.1.5 — Establish branch protection rules | Branch protection (T1+) |
| 1.1.8 — Enforce code reviews | Required PR review (T1+); two reviewers (T3) |
| 1.4.x — Require signed commits | Signed commits (T3) |
| 2.x — Build environment | Hosted builder (T2+); isolated builder (T3) |
| 3.x — Dependency management | SBOM (T2+); vulnerability scan (T1+); pinned deps via claims |
| 4.x — Artifact validation | Signed attestation (T2+) |
| 5.x — Deployment | Release pipeline contract (T2+) |

CIS's recommendations are detailed; the system covers the structural ones and leaves operational ones (e.g., specific tooling versions) to per-repo decisions.

## Threat model (T3 required, T2 recommended)

A threat model is **not** in the optional reading at lower tiers because lower tiers don't require it. At T3, the threat model is a separate document in the repo (e.g., `docs/THREAT-MODEL.md`).

### Minimum contents

- **Asset inventory** — data, credentials, systems, code, build infrastructure
- **Adversary profiles** — capability, motivation, access. Includes opportunistic, motivated external, insider, nation-state at T3.
- **Attack surface enumeration** — every interface the adversary could touch (API endpoints, file inputs, network sockets, IPC channels, deserialization paths, supply chain)
- **STRIDE per asset** (or equivalent threat enumeration) — Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege
- **Mitigations mapped to threats** — for each STRIDE finding, what reduces the risk
- **Residual risks** — what's left over after mitigations; link to exception registry where applicable
- **Refresh date** — refreshed annually at T3, or when the architecture materially changes

The threat model is not part of the audit document; it's a reference the audit cites. The audit at T3 includes a "Threat Model Status" line in the front matter:

```yaml
threat_model_ref: "docs/THREAT-MODEL.md"
threat_model_last_refreshed: "<ISO 8601>"
```

The verification script checks that `threat_model_last_refreshed` is within the last 365 days at T3.

## When reproducibility is not achievable

Reproducible builds are recommended at T3 but rarely achievable for all projects (container images in particular are notoriously non-reproducible in the wild).

The audit should document **why** reproducibility was not pursued, and **what alternative integrity properties are provided** (typically signed attestation from a hosted builder).

The standard normalization mechanism is `SOURCE_DATE_EPOCH` (a Unix timestamp consumed by build tools to normalize embedded timestamps), typically derived from the release commit's timestamp.

## How to include the framework mapping in a T3 audit

At T3, the audit document includes a section "Framework Mapping" with a table. Example:

```markdown
## Framework Mapping

| Framework | Requirement | Evidence in this audit |
|---|---|---|
| SLSA Build Level | L3 | Signed attestation in §"Build Attestation"; builder isolation verified per `.github/workflows/release.yml` |
| NIST SSDF | PW.7 (pre-release review) | Sign-off section; approver ≠ auditor |
| NIST SSDF | RV.2 (prioritize/remediate) | Exception registry; `.security/audits/exceptions.json` |
| OpenSSF Scorecard | Pinned-Dependencies | Claim MYAPP-CLM-002 verified (dependency_pinned) |
| SOC 2 CC8.1 | Approves | Approver: <name>, Approved at: <ISO 8601> |
| CIS SSC 1.1.8 | Code review | Two reviewers on the release PR (per branch protection) |
| HIPAA (if applicable) | <specific rule> | <evidence> |
```

This table is the part of the audit a SOC 2 auditor or federal procurement officer looks at first. Make it explicit.
